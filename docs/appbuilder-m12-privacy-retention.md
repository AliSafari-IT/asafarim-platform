# M12 Privacy and Retention Policy

Full policy table lives in code as the single source of truth:
`lib/retention/policy.ts#RETENTION_POLICIES` — this document explains it in
prose and records the scope decision behind each `automatedCleanup: false`
row.

## What is retained, for how long, and who can access it

| Category | Retention | Automated cleanup? | Who can access it |
|---|---|---|---|
| Prompts (M05 creation-request) | Lifetime of the app | No — deleted only with the app via a deletion request | App owner/editors; operators |
| Conversation messages (M08) | 180 days on an **archived** app; indefinite on an active one | No — eligibility computed, deletion operator-assisted | App owner/editors/viewers; operators |
| AI job diagnostics (`generation_jobs`/`modification_jobs`/`repair_attempts`.`usage`/diagnostic fields) | 90 days after the job reaches a terminal state | No — eligibility computed, deletion operator-assisted | App owner/editors; operators |
| Validation artifacts (screenshots/traces) | 30 days (`retention_expires_at`, set at creation) | **Yes** — `lib/retention/sweep.ts` | App owner/editors, until swept; operators |
| Test traces/screenshots | Same as validation artifacts (they're the same table, `kind: screenshot/trace`) | **Yes** | Same as above |
| Generated app data (records/files/activity) | Follows the app's own lifecycle (active/archived) | No — removed via the app's own reset/delete paths or a deletion request | Generated-app members (runtime, per row-access rules); app owner/editors; operators |
| Archived apps | Indefinite (archiving is reversible, not deletion) | No — deletion only via an explicit request | App owner; operators |
| Audit records (`audit_events`) | Indefinite — compliance/forensic record | No — never a sweep target | App owner (read-only); operators |
| File metadata and objects (`generated_files` + the object-storage bytes) | Follows the owning record/app's lifecycle | No — never a background TTL; a still-referenced file must never silently disappear | Generated-app members with read access to the owning record; app owner/editors; operators |
| Usage events (`usage_events`, the billing-readiness ledger) | Indefinite by design | No | Operators only |
| Operational events | 365 days | No (not yet automated) | App owner/editors (readiness UI, most recent 10); operators (full history) |

## Why several categories are eligibility-only, not automated, in M12

Automated deletion is irreversible. For `validation_artifacts` this is
low-risk: they're regenerated by re-running validation, and a
`retention_expires_at` is already set deterministically at creation with no
ambiguity about what "expired" means. Conversation history and AI
diagnostics are different — an app owner or editor may still find a
6-month-old conversation genuinely useful context, and choosing 180/90 days
as a hard cutoff for irreversible deletion is a product decision this
milestone does not make unilaterally. `lib/retention/eligibility.ts`
computes exactly which rows WOULD be eligible (and is unit-tested —
`lib/retention/eligibility.test.ts`), so turning on automated deletion for
these categories later is a small, well-scoped change, not a redesign.

## Running the retention sweep

```bash
pnpm --filter appbuilder retention:sweep          # dry run — reports only
pnpm --filter appbuilder retention:sweep --apply  # actually deletes
```

Dry-run is the default specifically so an operator never accidentally
deletes anything by running the command without thinking. A real `--apply`
run deletes the underlying object-storage bytes first, then the metadata
row — if the storage delete fails, the row is left in place so the next
sweep retries rather than orphaning a reference to nothing. Every applied
sweep records one `operational_events` row (`category: "storage"`, `kind:
"retention.swept"`) with the count deleted.

## Export and deletion-request foundations

`data_subject_requests` (`lib/db/schema.ts`) is a queue, not a fulfillment
engine — explicit M12 scope: a foundation, not a full compliance platform.
An operator sees a `kind: "export" | "deletion"` request, works it by hand
(pulling the relevant app's data via the existing repositories, or removing
it), and marks the row `completed`. There is no self-service UI for a user
to file one of these requests yet, and no automatic fulfiller. This is
explicitly the smallest viable foundation that makes a future self-service
flow additive rather than a rewrite: the schema and status lifecycle
(`received` → `in_progress` → `completed`/`rejected`) already exist.

## What needs operator intervention

- Any `data_subject_requests` row — always, by design (no automatic fulfiller exists).
- Conversation-message/AI-diagnostic deletion beyond the computed eligibility window — an operator must explicitly choose to delete, there is no automated sweep.
- Generated-app data on an app the owner wants permanently gone — archiving does not delete; only an explicit deletion request does, and that's operator-assisted.
- Anything the retention sweep's dry-run flags as eligible but that looks unexpectedly large — worth a manual sanity check before running `--apply`.
